2. How we are working

One section at a time. No section starts before the previous one closes.

BUILD locally → VERIFY → REPORT → COMMIT → DEPLOY → next section

"Done" means all five, not just the first:

  1. The feature works end to end from the interface — not only from the database.
  2. Empty, loading, error, unauthorised and failure states are handled.
  3. It works at desktop, tablet and phone widths.
  4. Keyboard reachable, labelled, visible focus.
  5. Lint clean, no PHP errors, and tested over HTTP rather than assumed.

That last point has already earned its place. Testing rather than assuming has caught, so far: a visibility rule that silently filtered WP-CLI queries; a duplicate auth cookie that worked in browsers but failed stricter clients; a seeder that created duplicate listings on every run; an Elementor autosave shadowing published data; and a stylesheet load order that stripped the height off every art-directed image.

3. Architecture as built

The dividing line

The test for every decision: if the theme were deleted and replaced tomorrow, would any listing, membership, inquiry, facility or relationship be lost? If yes, the code is in the wrong place.

Why Elementor free, and no Pro

Pro's value is its Theme Builder — header, footer, archive and single templates. Handoff §3.1 assigns every one of those to the custom theme, and §3.2 assigns the dynamic widgets to the custom plugin. Elementor free registers custom widgets through the same API as Pro. Milestone 1 explicitly asks for Elementor "without unnecessary add-ons".

Annual licences: £0.

The trade-off, stated plainly: without Pro the client cannot drag-and-drop the listing archive or single listing layouts — those stay theme-rendered and change through us. The handoff document anticipates exactly this ("templates … where Elementor alone is not appropriate"), so it is compliance rather than a gap. Everything they will realistically want to edit is editable.

Shortcodes first, widgets second

Every dynamic block has one implementation in TDH\Render and two entry points:

[tdh_hero_search] · [tdh_audience] · [tdh_property_grid] · [tdh_split_feature] · [tdh_owner_cta]

The shortcode is the primitive. It works in Elementor, Gutenberg, the classic editor, a widget area, or a template — and it keeps working if Elementor is ever deactivated. A widget-only approach would lock the client's content inside Elementor's own JSON, which handoff §2 forbids.

The Elementor widget is a thin wrapper around the same renderer. It exists for the structure tree: a page assembled from raw HTML collapses into a single "Text Editor" node, and the client ends up editing an entire homepage through one textarea. Named widgets give discrete, selectable sections.

Static marketing content has no shortcode on purpose where it does not read the database — but the audience cards and owner CTA are blocks rather than loose widgets, because a card grid has a fixed shape and loose widgets let someone delete one heading and leave a card with no title.

A full attribute reference lives in wp-admin at Listings → Shortcodes.

Design token system

All values live in assets/design-tokens.css: colour roles, a fluid type scale, a 4px spacing scale, containers, radii, shadows, motion. Component and section styles draw exclusively from tokens.

An audit of the stylesheet finds 0 hex colours, 0 raw rem literals, 400 var() references. What remains as raw pixels: 1px borders, the focus outline offset, the card hover lift, the screen-reader clip values, and media query breakpoints — CSS cannot use custom properties in a media condition.

Three decisions worth understanding

tdh_billing_hold is not tdh_paused. To a renter both are simply "not there". On renewal they must behave completely differently: only billing holds are restored. Without the distinction, a landlord who paused one of their three homes last week finds it silently republished the moment their card is fixed.

The street address is private. A furnished rental that sits empty, with its address published, is an easy target. Three guards, and the third is a release blocker: fields registered show_in_rest => false; never placed on a public template, not even hidden, because Elementor renders hidden elements into the DOM; and an explicit REST and page-source check in QA.

Never look up a listing by slug. A pending or draft post has no slug until first published, and custom statuses are excluded from post_status => 'any'. Records are found by a meta key we control. The seeder learned this by duplicating every pending listing on each run.

4. Demo importer

Tools → Import Demo Content. One button builds the whole demonstration site on any install: every public page, both menus, five Pittsburgh medical facilities, four furnished listings with photographs, and the homepage laid out in Elementor.

Verified from an empty database: 8 pages, 4 listings, 5 facilities, 4 photographs, 2 menus. Run three times — counts identical, no duplicates.

Photographs ship inside the plugin. An importer that downloads from a stock photo host fails on exactly the locked-down hosting a client is most likely to be on.

It is not automatic on activation. Activating a theme on a site that already has content would overwrite the client's menus and front page with no warning and no undo. It requires a deliberate click, a nonce, the capability to manage options, and it states what it will overwrite before it does.

5. Blockers

The first two cost money or time if they move late.

1. Membership pricing model — highest priority, needed at kickoff.
The delivery plan recommended one tier, up to three listings. The 8/16 feedback introduced per-listing pricing with 10% and 15% volume discounts. The prototype contains both, contradicting each other on adjacent screens. These are different products: one sells a membership, the other sells listing slots. It determines how many membership levels exist, how the allowance is enforced, and what happens when a landlord on the three-listing price deletes a listing. Stripe products are created in Milestone 1 and are awkward to restructure once real members exist.

2. EIN / tax ID and business identity — needed at kickoff.
A2P 10DLC registration cannot be submitted without it, and carrier vetting is the longest lead time on the project — one to three weeks that neither of us controls. It should be submitted in week 1 and run in the background, not started when we reach the SMS section.

3. Final name and domain. "ThirtyDayHomes", "30 Day Homes" and "WorkStay" are all in use across the spec and prototype. Touches hosting, Stripe, email authentication, the A2P brand registration and the logo. The wordmark reads from the site title, so this is cheap to change until accounts are created in a name.

4. Exact prices. Monthly and annual figures, and the two-months-free annual discount. The prototype's numbers are placeholders.

5. Subscription layer. Paid Memberships Pro or WooCommerce Subscriptions. We recommend PMPro — core and its Stripe gateway are free, and its status model maps cleanly onto ours. Migrating after real members exist is painful.

6. Approved SMS message template and consent wording. Needed before the SMS build, with the client's legal guidance on consent and opt-out.

7. The launch facility list — week 3. Which Pittsburgh hospital campuses go live, with addresses. The seeded coordinates are approximate placeholders and must not reach production.

8. Terms, Privacy, Fair Housing text — request week 1. Attorney-provided. The most common reason a finished site sits unlaunched. The attorney needs a written summary of what the site does and what data it collects — now including SMS.

Client feedback slower than two business daysThe schedule assumes it. Each slipped review moves the launch date by the same amount — flagged in the Friday update, not discovered at the end.

8. Deliberately not in V1

Preserved from spec §4: native mobile apps; renter payments, rent collection, escrow or deposit processing; two-way conversational SMS or in-app chat — the handoff document is explicit that SMS is notification only; video tours; background checks or identity verification; lease signing; advanced landlord analytics; dynamic pricing; recommendation engines; multi-language support; a separate site per city; and any custom payment infrastructure.

Also excluded, and worth naming because the prototype implies otherwise: property reviews and ratings. The prototype showed a hardcoded 4.9 star rating on every card. There is no review system in V1 and none is planned, so it has been removed — it promised social proof that would never exist.
